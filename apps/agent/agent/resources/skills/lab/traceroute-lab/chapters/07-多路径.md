# 第 7 章 多路径与重复探测

这一章处理真实网络里常见的情况：同一个 TTL 回来多个路由器。

## 本章目标

学完这一章，你应该能：

1. 解释同一个 TTL 为什么会回来多个不同的路由器；
2. 解释为什么一个 TTL 要发多个探测包（不只为了多路径）；
3. 用不同的目标端口给探测包编号；
4. 写一个“读满 N 个就进入下一 TTL”的接收循环；
5. 每个 TTL 内部去重，但不做全局去重。

---

## 7.1 同一个 TTL，为什么会有多个路由器

互联网上的路由器经常有多条“代价相同”的路径。比如：

```text
                 ┌── R2 ── R3 ──┐
你的电脑 ── R1 ──┤               ├── R6 ── 目标
                 └── R4 ── R5 ──┘
```

从你的电脑看：

- R2 和 R4 都离你 2 跳；
- R3 和 R5 都离你 3 跳。

路由器通常会用 **ECMP（Equal-Cost Multi-Path）**：有多条等价路径时，按“流”做哈希，把不同的流分到不同路径。

哈希通常看五元组：

```text
源 IP、目标 IP、源端口、目标端口、协议号
```

所以：

- 同一组五元组，通常一直走同一条路；
- 换一个目标端口，可能换一条路；
- 换一个目标地址，几乎肯定换一条路。

这就是为什么 traceroute 对同一个 TTL 发多个探测包：**每个探测包用不同的目标端口，尽量命中不同的路径。**

---

## 7.2 为什么一个 TTL 要发 3 个探测包（probe）

有两个动机，缺一不可：

### 动机 1：丢包

互联网是 best-effort，探测包可能丢，回包也可能丢。

如果每个 TTL 只发 1 个探测包，丢了就只能显示 `*`，你无法判断是“路由器不回”还是“包丢了”。

发 3 个，至少提高“有一个能成功”的概率。

### 动机 2：多路径

如上一节所说，不同的探测包可能走不同的路，从而带回不同的路由器。

| 每个 TTL 的探测包数 | 丢包时 | 多路径时 |
|---|---|---|
| 1 个 | 丢了就 `*` | 只能看到一条路径 |
| 3 个 | 有机会成功 | 有机会看到多条路径 |

`PROBE_ATTEMPT_COUNT = 3` 就是为此准备的。

> 注意：3 个不是“保证成功 3 个”，也不是“保证看到所有路径”。真实网络没有这个保证。自动评测环境会保证每个 TTL 命中所有路由器；本实验没有自动评测，所以看到一条路径也正常。

---

## 7.3 给探测包编号：用不同的目标端口

如果每个探测包都发到 33434，那么 ICMP 回包里的内层 UDP 目的端口全是 33434，你无法区分“这是第几个探测包的回包”。

让每个探测包用不同的目标端口：

```python
ports = [TRACEROUTE_PORT_NUMBER + i for i in range(PROBE_ATTEMPT_COUNT)]
# 例如 [33434, 33435, 33436]
```

发送：

```python
for port in ports:
    sendsock.set_ttl(ttl)
    sendsock.sendto(b"hello", (ip, port))
```

这样，ICMP 错误包的内层 UDP 目的端口就告诉你“这是发给哪个端口的探测包”。

> 端口范围 `[33434, 33464]` 是 Cisco 的惯例，不是正式标准。用 `33434 + i` 一定在范围内（3 个探测包最多到 33436）。
>
> 不同 TTL 会重复使用这几个端口。本实验先用这个简单做法；迟到包的风险见 7.7，更稳的过滤见 7.9。

### 为什么不用固定端口

固定端口也能跑通本实验的简单场景：你只要把“这个 TTL 收到的所有回包”都收集起来就行。但一旦出现：

- 重复回包；
- 迟到的上一跳回包；
- 同一台机器上其他程序留下的回包；

你就无法判断这个回包属于哪个探测包。用端口编号，至少有了一条线索。

## 7.4 接收循环：读满 N 个就停

不推荐写法（只考虑本实验回包时结果通常对，但会收进 Echo Reply/无关包，而且更慢）：

```python
# 不推荐：会多等 2 秒
routers = set()
while recvsock.recv_select():
    buf, _ = recvsock.recvfrom()
    routers.add(IPv4(buf).src)
```

为什么慢？

- 假设你发了 3 个探测包，也收到了 3 个回包；
- 第 4 次 `recv_select()` 没有包，会**再等 2 秒**才返回 False；
- 30 个 TTL 就是 60 秒的额外等待。

正确写法：**发几个，就最多读几个。**

```python
routers = set()

for _ in range(PROBE_ATTEMPT_COUNT):
    if not recvsock.recv_select():
        break
    buf, _ = recvsock.recvfrom()
    outer = IPv4(buf)
    routers.add(outer.src)
```

如果只收到 2 个，第 3 次 `recv_select()` 会超时 2 秒，然后进入下一 TTL。这是可以接受的（网络确实少回了一个）。

如果 3 个都很快回来，就不会有多余的 2 秒等待。

> 本实验只需要知道“发几个、最多读几个”。更细的超时处理属于进阶内容，不在本教程的验收范围内。

---

## 7.5 去重：每个 TTL 一个 set

同一个 TTL 内，同一个 IP 只应出现一次：

```python
routers = set()
...
routers.add(outer.src)
...
util.print_result(sorted(routers), ttl)
```

- `set` 自动去重；
- `sorted` 只是让输出稳定，题目不要求顺序；
- `print_result` 接受 `list[str]`，所以要把 set 转成 list。

**不要用全局 set。** 理由：

- 路由环路时，同一个路由器会在不同 TTL 重复出现；
- 本实验不处理环路，但如果你用全局 set，会把合法的重复跳删掉；
- 每个 TTL 独立去重，才符合“第 i 个子列表”的语义。

## 7.6 例子：沙箱里真实的多路径

2026-10-26 在沙箱里对 `8.8.8.8` 跑 3 个探测包/TTL，真实输出里同一个 TTL 出现了多个路由器：

```text
 5: 10.200.77.129
    10.200.77.137
 8: 101.95.246.149
    101.95.247.117
    101.95.247.157
 9: 101.95.224.141
    101.95.224.21
    101.95.224.25
11: 202.97.39.21
    202.97.39.57
    202.97.83.38
12: 202.97.25.226
    202.97.58.114
    202.97.6.50
```

对应的返回值片段是：

```python
[
    [],                                      # TTL=1
    [],                                      # TTL=2
    ["11.82.248.76"],                        # TTL=3
    [],                                      # TTL=4
    ["10.200.77.129", "10.200.77.137"],      # TTL=5
    ["101.226.210.70"],                      # TTL=6
    [],                                      # TTL=7
    ["101.95.246.149", "101.95.247.117", "101.95.247.157"],  # TTL=8
    ...
]
```

这说明：

- TTL=5、8、9、11、12 都出现了多个等价路由器；
- 同一 TTL 的路由器数量不一定等于 3（TTL=5 是 2 个，TTL=8 是 3 个）；
- TTL 1、2、4 是空列表；TTL 3 这次有 `11.82.248.76`（单 probe 那次没有）；
- 每次运行的 IP 和数量都可能变化。

> 这是真实抓包，不是理想拓扑。真实网络可能只给你其中一条路径，也可能像这里一样给出多条；两种都正常。

## 7.7 真实网络提醒

- **ECMP 按流哈希**：同一组五元组通常固定走一条路。你换了目标端口，才可能换路。
- **不是所有路由器都回 ICMP**：某一跳 `*` 很正常。本次单 probe 实测 TTL 1–4 全是 `*`，3 probe 参考实现在 TTL 3 抓到了 `11.82.248.76`；TTL 3 有时有、有时没有。
- **路径可能变化**：同一次实验里，系统 `traceroute` 在 TTL 15 到达 `8.8.8.8`，Python 参考实现到 TTL 16 才到达；IP 也不同。这是正常的。
- **NAT 会影响**：沙箱出网经过 NAT，ICMP 错误包的**内层源地址**被改写成 `192.168.0.99`（不是沙箱 `169.254.68.6`）；不要用内层源 IP 判断“是不是我的包”。
- **迟到包可能占名额**：上一跳的回包如果迟到，可能被这一跳的接收循环读走。本实验可以先接受这个风险；如果明显影响结果，重跑一次，或用 7.9 的过滤（可选）。
- **没有自动评测的保证**：自动评测环境会保证命中所有路由器；本实验不会。你看到单路径，不代表实现错；你看到多路径（如 TTL 5/8/9/11/12），也不必惊讶。

如果你很想观察多路径，可以：

1. 换几个不同目标（不同自治系统/不同地区）；
2. 换目标端口（`33434 + i` 已经做了）；
3. 多跑几次；
4. 用系统 `traceroute -n` 对照，看它是否也显示多路径。

不要为了“制造多路径”去改端口到奇怪的值；真实路由器可能只对 33434–33464 回 Time Exceeded。

## 7.8 代码：多探测包版本

把第 6 章的 `traceroute()` 改成：

```python
def traceroute(sendsock: util.Socket, recvsock: util.Socket, ip: str) \
        -> list[list[str]]:
    result: list[list[str]] = []

    for ttl in range(1, TRACEROUTE_MAX_TTL + 1):
        ports = [TRACEROUTE_PORT_NUMBER + i
                 for i in range(PROBE_ATTEMPT_COUNT)]

        for port in ports:
            sendsock.set_ttl(ttl)
            sendsock.sendto(b"hello", (ip, port))

        routers = set()
        for _ in range(PROBE_ATTEMPT_COUNT):
            if not recvsock.recv_select():
                break
            buf, _ = recvsock.recvfrom()
            outer = IPv4(buf)
            routers.add(outer.src)

        util.print_result(sorted(routers), ttl)
        result.append(sorted(routers))

    return result
```

这个版本比第 6 章多了：

- 每个 TTL 发 3 个探测包；
- 每个探测包用不同端口；
- 最多读 3 个回包；
- 用 set 去重。

> 端口编号在这个版本里的直接作用是**改变五元组**，增加命中不同路径的机会；主循环仍然只按 `outer.src` 收集，不靠端口匹配。想靠端口匹配，用 7.9 的过滤器。

它仍然没有：

- 过滤无关包（可能把 Echo Reply 当成路由器）；
- 终点判定（到了还继续跑）；
- 处理重复/迟到包（进阶内容）。

先跑通这个版本，再进入第 8 章。

## 7.9 进阶（可选）：只接受“我们的”回包

如果你发现输出里混进了奇怪的 IP，可以加一层过滤。利用第 4、5 章的解析：

```python
def relevant(buf: bytes, ip: str, ports: list[int]):
    outer = IPv4(buf)
    if outer.proto != 1:
        return False

    icmp_off = outer.header_len
    icmp = ICMP(buf[icmp_off:icmp_off + 8])
    if icmp.type not in (3, 11):
        return False

    inner_off = icmp_off + 8
    inner = IPv4(buf[inner_off:])
    if inner.proto != 17 or inner.dst != ip:
        return False

    udp_off = inner_off + inner.header_len
    udp = UDP(buf[udp_off:udp_off + 8])
    return udp.dst_port in ports
```

然后在接收循环里：

```python
if not relevant(buf, ip, ports):
    continue
routers.add(IPv4(buf).src)
```

注意：这个过滤器会增加“读满 N 个”的复杂度，因为无关包会消耗一次循环。更稳的做法是用 `while` + 计数 + 超时预算，但那就是进阶内容的范围了。本实验可以先不做。

## 7.10 本章验收

- [ ] 每个 TTL 发 `PROBE_ATTEMPT_COUNT` 个探测包；
- [ ] 每个探测包用不同的目标端口；
- [ ] 接收循环最多读 `PROBE_ATTEMPT_COUNT` 个包；
- [ ] 每个 TTL 用独立的 set 去重；
- [ ] 在真实沙箱里至少观察到一个多路径 TTL（例如 TTL 5/8/9/11/12）；
- [ ] 没回包时打印 `*`，不崩溃；
- [ ] 3 个回包都很快时，不会多等 2 秒；
- [ ] 能解释“为什么发了 3 个，可能只收到 1 个”。

## 7.11 常见误区

| 误区 | 纠正 |
|---|---|
| 只发 1 个探测包，认为多路径靠运气 | 每个 TTL 发 `PROBE_ATTEMPT_COUNT` 个 |
| 所有探测包用同一个端口 | 用 `33434 + i` 区分 |
| `while recv_select()` 排空队列 | 读满 N 个就停；否则每跳多等 2 秒 |
| 用全局 set 去重 | 每个 TTL 独立 set；环路需要重复跳 |
| 用内层源 IP 判断探测包 | NAT 可能改写；用内层目的 IP + UDP 目的端口 |
| 看到单路径就以为代码错 | 真实网络不保证多路径 |
| 把 `PROBE_ATTEMPT_COUNT` 改成 10 | 探测包越多越慢；3 是教程的折中 |
| `print_result` 在探测循环里调用 | 每个 TTL 汇总后调一次 |
