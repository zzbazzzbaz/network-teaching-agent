# 第 6 章 最小实现：从单 TTL 到循环

这一章把前面零散的操作串成一次完整探测，再循环到 30 跳。

## 本章目标

学完这一章，你应该能：

1. 把“发一个包、收一个包、解析、取源 IP”串成一次完整探测；
2. 用单个 TTL 拿到一个可见路由器（TTL=1/2 可能没有回包，建议先用 TTL=8）；
3. 用循环跑完 1–30 跳；
4. 正确处理“没有回包”的情况；
5. 返回符合契约的 `list[list[str]]`。

这一章的版本还**不会在目标处停止**，也**不会处理多路径**。这是故意的：先把最小闭环跑通，再逐步加功能。

---

## 6.1 一次探测的完整生命周期

```text
1. set_ttl(ttl)
2. sendto(payload, (ip, port))
3. recv_select()  ← 等最多 2 秒
4. recvfrom()     ← 只有第 3 步为 True 才调用
5. IPv4(buf)      ← 解析外层 IP 头
6. outer.src      ← 这个回包是谁发的
```

把这 6 步写成一个函数，就叫 `probe_ttl`。

> 第 2 章的脚本叫 `probe_once.py`；这里的函数叫 `probe_ttl`。名字像，但不是同一个东西：脚本是单独运行的，函数是 `traceroute.py` 里的辅助函数。

---

## 6.2 写 `probe_ttl`

在 `traceroute.py` 里，`traceroute()` 之前加一个辅助函数：

```python
def probe_ttl(sendsock: util.Socket, recvsock: util.Socket,
              ip: str, ttl: int):
    sendsock.set_ttl(ttl)
    sendsock.sendto(b"hello", (ip, TRACEROUTE_PORT_NUMBER))

    if not recvsock.recv_select():
        return None

    buf, _ = recvsock.recvfrom()
    outer = IPv4(buf)
    return outer.src
```

几个细节：

- `set_ttl` 必须在 `sendto` 之前；
- `payload` 用 `b"hello"` 就行，内容不重要；
- `recv_select()` 返回 False 表示 2 秒内没有回包，返回 `None`；
- `recvfrom()` 返回的 `buf` 从外层 IPv4 头开始，所以 `IPv4(buf)` 能直接解析；
- 这里暂时不检查包是不是 ICMP、是不是我们的探测。先假设“收到的就是我们的回包”；第 7.9 节和第 8.1 节会给出可选的过滤思路。

> 如果你在 `probe_ttl` 里用 `IPv4(buf[:20])`，也能工作，因为 `IPv4.__init__` 只读前 20 字节。但传完整 `buf` 更清楚，也不会在以后加 options 时踩坑。

## 6.3 单 TTL 跑通

先不要写循环。在 `traceroute()` 里临时写：

```python
def traceroute(sendsock, recvsock, ip):
    router = probe_ttl(sendsock, recvsock, ip, 8)
    print("TTL=8:", router)
    return []
```

运行：

```bash
python3 traceroute.py 8.8.8.8
```

真实沙箱里，你看到的可能是：

```text
TTL=8: 101.95.246.149
```

也可能是 `101.95.247.117`、`101.95.247.157` 等——同一个 TTL 有多个等价路由器，每次运行可能不同。

如果你看到 `None`，回到第 2 章检查：

- TTL 设置了吗？
- 目标端口对吗？
- `recv_select()` 是否超时？
- 系统 `traceroute -n 8.8.8.8` 在 TTL=8 能看到东西吗？

**不要用 TTL=1 做第一次验证。** 沙箱里 TTL=1/2 通常没有回包；TTL=8 的 33434 实测更稳。确认 TTL=8 能拿到回包，再往下写。

---

## 6.4 循环 1–30

把临时代码换成：

```python
def traceroute(sendsock: util.Socket, recvsock: util.Socket, ip: str) \
        -> list[list[str]]:
    result: list[list[str]] = []

    for ttl in range(1, TRACEROUTE_MAX_TTL + 1):
        router = probe_ttl(sendsock, recvsock, ip, ttl)
        routers = [] if router is None else [router]

        util.print_result(routers, ttl)
        result.append(routers)

    return result
```

运行：

```bash
python3 traceroute.py 8.8.8.8
```

输出可能像（2026-10-26 沙箱真实输出，单 probe 版本）：

```text
traceroute to 8.8.8.8 (8.8.8.8)
 1: *
 2: *
 3: *
 4: *
 5: 10.200.77.129
 6: 101.226.210.66
 7: *
 8: 101.95.246.149
 9: 101.95.224.141
10: 202.97.62.186
11: 202.97.12.206
12: 202.97.111.62
13: CTCN2.DE.FRK.CTGNet (203.22.178.189)
14: CTCN2.CN.HKG.CTGNet (203.22.178.22)
15: *
16: dns.google (8.8.8.8)
17: dns.google (8.8.8.8)
...
30: *
```

说明：

- 这次单 probe 的 TTL 1–4 是 `*`，因为那些路由器没有回包；3 probe 版本可能在 TTL 3 就看到 `11.82.248.76`；
- TTL=5 才第一次看到路由器；
- **因为还没有写“到达就停止”，16 跳之后还在继续发**，所以 17–29 反复显示 `dns.google (8.8.8.8)`，30 跳是 `*`；
- `routers` 是当前 TTL 发现的 IP 列表；
- 没回包时是空列表，`print_result` 会打印 `*`；
- `result` 收集每个 TTL 的列表；
- 循环固定跑满 30 跳，不会因为到了目标而停。

这正是第 8 章要解决的问题：**知道到了，就停。**

---

## 6.5 超时的代价

`SELECT_TIMEOUT = 2`，所以一个没有回包的 TTL 最多等 2 秒。

最坏情况：30 跳全都没有回包 → 30 × 2 = **60 秒**。这是正常的，不是卡死。

如果你觉得太慢，不要改 `util.py` 的 `SELECT_TIMEOUT`；先确认：

- 目标是否可达？
- 系统 `traceroute` 是否也全是 `*`？
- 你的 TTL/端口是否设置正确？

第 7 章会通过“一个 TTL 发多个探测包”来减少“只发一个包、恰好丢了”的概率，但不会消除 2 秒超时。

> 如果你在终端里看到程序停住，先等 2 秒；`recv_select` 超时后会继续下一跳。

## 6.6 返回值契约

`traceroute()` 返回 `list[list[str]]`：

```python
[
    [],                    # TTL=1，没回包
    [],                    # TTL=2，没回包
    [],                    # TTL=3，没回包
    [],                    # TTL=4，没回包
    ["10.200.77.129"],     # TTL=5
    ["101.226.210.66"],    # TTL=6
    [],                    # TTL=7
    ["101.95.246.149"],    # TTL=8
    ...
]
```

规则：

- 第 i 个子列表对应 TTL = i+1；
- 子列表内顺序任意；
- 没发现路由器时可以是空列表；
- **每个 TTL 都要 append 一个子列表**，即使是空的。不要因为没回包就跳过，否则后面的 TTL 会错位；
- 现在不要求最后一跳是目标；第 8 章再加。

一个常见错误是只在收到回包时 append：

```python
# 错误：没回包就不 append，导致 result[2] 对应的是 TTL=4
if router is not None:
    result.append([router])
```

正确做法是先决定 `routers`（空或非空），再统一 `append`。

## 6.7 现在还没做的三件事

| 没做 | 会在哪一章补 |
|---|---|
| 到达目标就停止 | 第 8 章 |
| 同一 TTL 发多个探测包、收集多个路由器 | 第 7 章 |
| 过滤无关包、去重 | 第 7.9 / 8.1 节（可选） |

所以现在看到“到了目标还继续跑”“同一跳只有一个 IP”“偶尔把同一台机器上其他程序的包当成自己的”，都是预期的。

## 6.8 动手：观察三件事

1. 把 `TRACEROUTE_MAX_TTL` 临时改成 5，跑一次，确认只打印 5 跳；改回 30。
2. 对 `1.1.1.1` 和 `8.8.8.8` 各跑一次，比较前几跳是否相同。
3. 找一台不存在的主机（比如 `192.0.2.1`），跑一次，观察是否跑满 30 跳（可能全 `*`，也可能看到网关/中间跳的 unreachable 或 Time Exceeded），以及大概花了多久。

> `192.0.2.0/24` 是文档保留地址，通常不可达；用它做“不可达”实验不会影响真实服务。

## 6.9 本章验收

- [ ] `probe_ttl` 能返回一个路由器的 IP（沙箱里 TTL=8/33434 更稳定），或在无回包时返回 `None`；
- [ ] `traceroute` 能按 TTL=1…30 打印；
- [ ] 每个 TTL 都 append 了一个子列表（包括空列表）；
- [ ] 没回包时打印 `*`，程序不崩溃；
- [ ] 返回值的类型和长度符合契约；
- [ ] 能解释为什么现在不会在目标处停止。

---

## 6.10 常见误区

| 误区 | 纠正 |
|---|---|
| TTL 从 0 开始 | IPv4 TTL 从 1 开始；0 通常非法 |
| 先 `sendto` 再 `set_ttl` | TTL 设置必须在发送前 |
| 没回包就不 append | 会导致后面的 TTL 错位；空列表也要 append |
| `print_result` 放在循环外 | 应该每个 TTL 调一次 |
| `recvfrom` 前不 `recv_select` | 可能阻塞或抛异常 |
| 把 `outer.src` 当成目标 | 中间路由器也会回包；目标判定是第 8 章 |
| 返回 `None` 或 `set` | 契约是 `list[list[str]]` |
| 改 `SELECT_TIMEOUT` 来“加速” | 会更容易误判无响应；先找真正原因 |
| 从 TTL=1 开始，没回包就以为代码错 | 沙箱里 TTL=1–4 经常是 `*`；先用 TTL=8 验证 |
| 到了目标还继续打印 | 第 6 章还没写停止；17–29 反复出现目标 IP 是正常的 |
